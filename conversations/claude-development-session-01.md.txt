  1. Available quantity can't go negative

  Available now stops at 0. Your example (6 tablets, 1 damaged, 5 held) already

  give -1. It now gives 0, both in the service and on the status screen.

  2. One person at a time for an individual item

  I added AvailabilityService.EnsureCanTake(item, activeLines, quantity).
  Checkout (Story 2.1) and approval requests (Story 3.1) must call it before
  giving out an item:

  - Already out or held by someone: rejected with a 409 and the message "…is
    already checked out or held by someone else". Pending approval requests
    count, so a second person can't request the drone while Hamza is deciding on
    the first.
  - Damaged: rejected with a 400.
  - Quantity other than 1: rejected for individual items.
  - Counted items: a quantity below 1 or above what's available is rejected.

  The "at the same moment" case

  The check above isn't enough on its own. Two people can both pass it before
  either saves. The guard against that is the rowversion on the equipment row.
  The second save fails, and the error handler already turns that into a 409
  with "Someone else just changed this equipment". A test confirms the database
  really rejects the second writer.

  There is no checkout endpoint, so nothing in the running app calls
  EnsureCanTake yet. Story 2.1 will wire it in, and its tests will fire two
  checkouts at once to prove only one succeeds.

● Here's how to run it from Visual Studio.

  Visual Studio (green play button)

  1. Open EquipmentTracker.sln from the project folder.
  2. In the toolbar, check that the startup project is EquipmentTracker.Api. If
     it isn't, right-click that project in Solution Explorer and choose Set as 
     Startup Project.
  3. Next to the green button, make sure the profile dropdown says http. It's
     the only profile I set up.
  4. Click the green button, or press F5.

  The browser opens at http://localhost:5007 and shows the equipment list. A
  console window also opens. Leave it open while you use the app, and close it
  or press Shift+F5 to stop.

  On the first run the app creates the EquipmentTracker database in LocalDB and
  fills it with the demo equipment and people, so there is nothing to set up.
  LocalDB is already installed on your machine.

  From a terminal instead

  dotnet run --project src/EquipmentTracker.Api

  Then open http://localhost:5007 in your browser. Stop it with Ctrl+C.

  Running the tests

  In Visual Studio, open Test > Test Explorer and click Run All. Or run dotnet 
  test in the project folder.

  If something goes wrong

  - "Address already in use": another copy is still running. Close its console
    window, or end the EquipmentTracker.Api process in Task Manager.
  - Page says it could not load equipment: the app isn't running. Start it again
    with the green button.
  - Database error on start: run sqllocaldb start MSSQLLocalDB in a terminal and
    try again.
  - Using VS Code, not Visual Studio: use the terminal command above. VS Code
    has no green button for this project unless you add a launch configuration,
    and I haven't set one up.

  At the moment the screen is read-only. Checking items out arrives in Story
  2.1, so you'll see everything as Available until then.

  How CheckoutService works, in order:
  1. It rejects an empty list, a duplicate item, or a due date before today
     (Pakistan time).
  2. For each item it calls availability.EnsureCanTake(...), the guard from
     Story 1.2. That blocks damaged items, items someone already holds, and
     quantities above Available.
  3. It creates one Checkout with one CheckoutLine per item, with status Out.
  4. It writes one CheckedOut history event per line. The checkout and its
     history are saved together or not at all.

  Your two rules:
  - Available never goes negative. EnsureCanTake refuses a quantity above
    Available, and a test checks this.
  - One person at a time. The guard blocks a second checkout of the same single
    item with a 409.
  - Simultaneous checkouts. When two people click at the same instant, the
    RowVersion check lets only one through. A test fires both at once and
    exactly one succeeds. It does this by marking the equipment row as touched
    (IsModified = true), so its RowVersion changes when saved.
  - Kits are all-or-nothing. If one item in a kit is unavailable, nothing is
    checked out.

  One call of mine to check. Items with "needs approval" (the Drone) are refused
  here with a clear message. The approval request flow is Story 3.1, so this
  keeps them from bypassing the approver in the meantime.

  How it works:
  - Single item, returned fine. The line becomes Returned and the item is
    available again.
  - Single item, returned damaged. The item's condition becomes Damaged and the
    note is saved. It is blocked from checkout until Story 4.1 (restore).
  - Counted items. You can return some now and the rest later. The line stays
    Out until everything is back. Damaged units are added to DamagedQuantity, so
    they drop out of Usable and Available stays correct and never negative.
  - Kits. Each item is returned on its own. If only the tripods come back, the
    Total Station stays checked out, which is your decision D2.
  - Errors. You can't return more than is outstanding, the damaged count can't
    exceed the returned count, and a line can't be returned twice (409). Each
    return writes one Returned history event.

  - Who returned it. The history records the person who borrowed the item as the
    one returning it. There's no "who is returning" picker, since returning has

  - Damaged counts in the history. For counted items, the number damaged goes

  - One shared damage note. An item has a single condition note, so a newer

    - Owner or Office, with a PIN, picks a From and To date and gets one row per
      item taken out. Each row shows borrower, item, quantity, checked-out
      date, due date and return date.
    - A row is included if the item was out at any point in the range, so items
      still out appear with "STILL OUT" and no return date. A partial return
      shows "2 of 4 returned".
    - Pending and rejected requests aren't listed, because they were never out.
    - There are no PUT, PATCH or DELETE endpoints for history, and tests confirm
      those calls fail.
  - 5.2 Corrections.
    - Only the Owner, with their PIN, can add a correction, and it needs a note.
    - It is stored as a new Corrected entry that points at the original and
      shows beside it. The original isn't touched, and a test compares it before
      and after.
    - Staff and Office, and a wrong PIN, all get a 403.

  Manual UI test steps

  6. Set From later than To. You should get a clear error.

  Issues and unmet acceptance criteria

  - I fixed a mistake in Story 4.1. PRD FR-21 says the Office or Owner can
    restore, but I had made it Office-only. Tariq can now restore as well. The
    test that expected Tariq to be refused is now a test that he is allowed, and
    Staff are still refused. No other 4.1 criteria changed.
  - The test suite needed a fix to stay reliable.
    - With 12 test classes, xUnit ran them all at once and overloaded LocalDB,
      which caused connection timeouts. One run failed 130 of 206 tests with a
      LocalDB timeout. I now cap parallel threads at 3 in TestSettings.cs. This
      is also very likely the cause of the two earlier flaky runs in Epic 3,
      though I had not confirmed that at the time.
    - I deleted one leftover test database from the killed run, and none remain.
      The suite now takes about 17 to 27 seconds.
  - History uses POST for search. The PIN travels in the body like every other
    protected action, and the endpoint only reads.
  - Corrections limits:
    - Only checkout and return entries can be corrected. Restores and approvals
      are recorded but have no correction path, because the history list is
      built from checkouts and returns.
    - A correction can't itself be corrected, so the correction points at the
      original entry.
    - Neither limit is stated in epics.md, so tell me if you want either one
      removed.
  - Not unmet, but worth knowing: the history query loads all checkout lines and
    filters by date in memory. That's fine for 25 staff, but it would need a
    database-side filter if the data ever grew large.
