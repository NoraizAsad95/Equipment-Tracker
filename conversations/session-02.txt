  Bugs to fix first

  1. Editing equipment shows the wrong fields. editEquipment in
     wwwroot/manage.js:135 never calls updateEquipmentForm().
     - Click Edit on a counted item like Tripod and the "Total quantity" field
       stays hidden. The "Needs approval" checkbox still shows, so you can't
       change a total.
     - It's the reverse for the next item you edit after a counted one.
     - The fix is one line: call updateEquipmentForm() at the end of
       editEquipment.
  2. The History page's default date range is wrong overnight. history.js:105
     uses toISOString(), which gives the UTC date. The server works in Pakistan
     time (UTC+5), so between 00:00 and 05:00 the default "To" date is yesterday
     and today's checkouts are left out. Use a local-date format instead.
  3. "Still out" rows on the History page aren't red. history.js:68 gives them
     the classes name overdue, but the CSS only styles .detail.overdue, so
     nothing happens.
  4. Save errors are hard to see on the Manage page. #message sits at the top of
     <main>. If you save at the bottom, for example with a wrong PIN, the error
     appears off-screen. Show it near the form, or make it sticky.

  UI and CSS

  - The most-used controls weren't redesigned. The Return, Approve/Reject and
    Restore forms inside each item card (app.js:28-154) are plain inline inputs
    with no styling. They'll wrap badly inside the narrow cards (about 19rem).
    Those cards are where staff spend most of their time, so they matter most.
  - The three pages look inconsistent. Only index.html has the new header
    (.equipment-header). manage.html and history.html still use the old plain
    header with a "← Back" link, and the History page has no redesign at all.
  - The stylesheet has layered overrides. styles.css was appended in blocks:
    - main, li.item, .top, .badge and .detail are each defined twice.
    - li.row is unused.
    - Indentation mixes 2 and 4 spaces and nests rules oddly.
    - Colors are hard-coded hex, so a few CSS variables and one merged pass
      would help.
  - Smaller UI problems:
    - The sticky header has no z-index, so cards with shadows can paint over it.
    - White text on the orange .CheckedOut badge (#ef6c00) is about 3.2:1
      contrast, below the AA minimum (4.5:1).
    - Buttons have no :focus-visible style, and #search:focus { outline: none }
      leaves only a faint shadow.
    - The due-date input has no min and no default.
  - manage.js is reformatted unevenly. Its 4-space blocks sit next to the
    original 2-space ones.

  Backend and security

  - PINs can be guessed. They are 4–6 digits with no lockout or rate limit. The
    Owner role guards manage and correct actions, so this is the biggest
    security gap.
  - Demo PINs are always seeded. Program.cs runs Migrate() and SeedData on every
    start, so the Owner PIN is 1111 wherever it runs. Limit seeding to
    Development, or require a first-run setup.
  - No HTTPS. There's no UseHttpsRedirection or HSTS, so PINs travel in plain
    text unless the host adds TLS.
  - Concurrency is only partly protected.
    - Only Equipment has a RowVersion.
    - ApprovalService touches neither the equipment row nor the line. A
      double-click on Approve can write duplicate history events, and a
      simultaneous approve and reject lets the last write win. The same fix as
      in ReturnService (modify the equipment row) would close it.
  - History search loads the whole database. HistoryService.SearchAsync loads
    every checkout line and every event, then filters by date in memory. That's
    fine at this size but will slow down with real history, so move the date
    filter into the query.
  - Smaller backend points:
    - RestoreService returns 404 before checking the PIN, so it reveals which
      item IDs exist.
    - The Correct button shows for Office users, but only Owners can use it.
    - Rejected requests never appear in History, even though they're recorded.

  Frontend robustness

  - The return, decide and check-out handlers in app.js have no try/catch. On a
    network failure, nothing is shown.
  - Their buttons stay clickable during a request. A double-click on Check out
    can create two checkouts for counted items.
  - After a successful check-out the form keeps the old due date and quantities.

  What's good

  - The services are cleanly separated.
  - History is append-only, and a correction is a new entry.
  - All DOM text goes through textContent, so there's no XSS risk.
  - There's one generic error for failed PIN checks.
  - The tests are thorough.
  - The responsive grid and the redesigned check-out panel and Manage rows are
    clean and consistent.
